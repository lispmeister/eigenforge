## Decisions

| Decision | Rationale | Consequences / Follow-up |
|----------|-----------|--------------------------|
| Use one local SQLite command ledger per core node. | Avoids central database connection pressure and fits future multi-core operation. | V1 treats one core as a one-member consensus group; V2 requires quorum evidence before action-authorizing appends. |
| Keep core persistence limited to finalized OODA/control facts. | IO sensor and actuator telemetry volume is large and belongs outside core. | Home Assistant, simulator streams, and later historian systems own telemetry; core stores decisions, capability/policy checks, commands, faults relevant to OODA, and after-action events. |
| Make catch-up append-only. | Network repair must not violate each node's local hash chain. | Lagging nodes append local catch-up evidence events; they must not copy foreign ledger rows, preserve foreign sequences, reuse foreign event hashes as local hashes, or splice missing records into the local chain. |
| Treat projections as mutable read models, not ledger. | Dashboards need efficient current state, but projections must not become authority. | Projection rows may be rebuilt or updated; `ledger_events` remains insert-only and authoritative. |
| Update tickets to encode the new storage model. | Future implementation work should not drift back to Postgres/advisory-lock assumptions. | `eig-pp46`, `eig-o1sj`, `eig-5u7f`, `eig-ibl4`, `eig-tvgt`, `eig-20dl`, `eig-193d`, and `eig-o1bf` now reference local SQLite, append-only, and consensus/catch-up constraints. |
