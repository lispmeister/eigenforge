## Decisions

| Decision | Rationale | Consequences / Follow-up |
|----------|-----------|--------------------------|
| Replace `observe/1` with `observe/2` rather than a separate `observe_with_snapshot/2` name. | The ticket specified "observe/1 accepts a pre_command_snapshot argument (or observe/2 is added)"; adding a default keeps all existing callers working while enforcing the correct behaviour when a snapshot is passed. | All callers updated; no dead code left. |
| Keep `@core_node_id "core_a"` module attribute as the fallback default in `CommandIssuer`. | Existing tests and the Trace module do not pass opts; a hard removal would break them. The spec requirement is that the runtime value overrides the default, which it now does via `Keyword.get/3`. | Trace.ex still uses the hardcoded atom via `@core_node_id`; a follow-up could thread the value from RuntimeConfig into Trace. |
| Emit `stale_snapshot_denied` by appending a second event after `policy_decision_recorded`, reusing the same PolicyDecision payload. | Spec §11 requires them as separate events with the same correlation_id. The PolicyDecision struct is already the natural payload for both; a new summary struct would add contract complexity without information gain. | Callers that pattern-match on event_type will now see two separate rows; the stale-deny event_id uses `refs.stale_deny_event_id` which was already computed in `event_refs/1`. |
| Change `recover_pending_commands/1` to query ALL rooms (no room_id filter). | Spec §9 requires every pending command to be resolved before issuing new commands. A restarted subscriber sharing a DB with another room's stale pending command must still resolve that command (via timeout) so the next subscriber for that room starts clean. | A subscriber restarted for room-a will now also time out room-b's stale commands if room-b's subscriber is down. This is safe because the `after_action_recorded` write clears `pending_command_id` in the projection; a later room-b subscriber restart will find nothing to recover. |
| Use `Exqlite.Sqlite3` low-level API (not `Exqlite.Basic`) for `LedgerSQLite`. | `Exqlite.Basic` wraps connections in a GenServer, adding supervised-process overhead that is unnecessary for a module that opens short-lived connections per operation. The ticket acceptance criteria require parameterized inserts and WAL mode; neither requires a long-lived connection process. | Each `append_event/2` call opens and closes a connection. A future ticket could add a supervised connection pool if throughput demands it. |
| Split `init_sql()` multi-statement string into a list of individual statements for `execute/2`. | `sqlite3_exec` supports multiple statements in one call, but separating them gives clearer error attribution per statement during initialization. | `init/2` now loops over five separate SQL strings; any one can be identified as the failing step from the error tuple. |

## Open Questions / Next Steps

- `Trace.ex` still carries a hardcoded `@core_node_id "core_a"` module attribute; it does not pass opts to `CommandIssuer.issue`. A follow-up could thread `RuntimeConfig.core_node_id` into the trace runner if deterministic multi-node trace testing is needed.
- `LedgerSQLite` opens and closes a SQLite connection per operation. If ledger throughput becomes a concern, a supervised connection process (e.g., wrapping `Exqlite.Sqlite3` in a GenServer or using `db_connection`) is now straightforward to add without changing the public API.
- The two-room recovery test relies on a restarted subscriber for room-a timing out room-b's command. This works but is an architectural side-effect. A cleaner design would have a dedicated recovery supervisor that queries all pending rooms at startup before handing off to per-room subscribers.
