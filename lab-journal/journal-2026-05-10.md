## Decisions

| Decision | Rationale | Consequences / Follow-up |
|----------|-----------|--------------------------|
| Keep the V1 spec executable and explicit rather than broad and suggestive. | Ambiguous prose would make independent implementation tickets diverge, especially golden traces and ledger behavior. | Future tickets can quote exact V1 rules for stale paths, event cardinality, idempotency, startup behavior, and trace determinism. |
| Treat schema/prose drift as a V1 contract failure. | The project uses schemas and generated modules as the shared ABI; mismatched enum or field names create silent runtime drift. | Schema, generated module, prose, and golden traces must be updated together. |
| Keep SQLite mutation rejection triggers in V1, but defer OS/process permission hardening. | The original spec contradicted itself by including mutation triggers in the first slice while deferring "permissions and mutation triggers." | V1 implementation keeps DB-level append-only rejection; broader operational hardening is deferred. |
| Make the deterministic rules reasoner own the idempotent fan already-in-state no-action outcome. | This prevents both core gate logic and reasoner logic from rewriting the same decision. | Core still owns sequencing, validation, policy, persistence, command issuance, and after-action observation. |
| Define V1 mailbox receipt trust as signed evidence, not independent SQLite proof by IO. | IO does not connect to core SQLite in V1, so "committed decision" verification needed an authority source. | V2 will replace this single-node shared-HMAC trust rule with quorum evidence. |
